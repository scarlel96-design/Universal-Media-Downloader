# WO-00R 개선 권고

조사일: 2026-11-01. 예상 속도는 측정값이 아니므로 적지 않는다. 경쟁 제품의 고유 코드를 가져오지 않는다. 근거 없는 기능은 맨 아래 별도 제안으로 둔다.

기준 구현은 커밋 `56d8c0e`의 WO-03이다. WO-04는 `feat/wo04-browser-extraction`에만 있다.

## 다운로드 작업 큐

- 기존 구현: 메모리 큐와 상태 문자열. 한 다운로드 스레드가 엔진을 돌린다.
- 관찰된 경쟁 제품 동작: 미확인. 스레드 72는 프로세스 전체 값이다.
- 개선할 구조: 바꾸지 않는다. 큐 상한을 경쟁 제품에 맞출 숫자가 없다.
- 사용할 공개 오픈소스: 표준 라이브러리 `queue`와 현재 `asyncio` 큐.
- 예상 개발 난이도: 변경 없음.
- 추가 비용: 0.
- 기술적 위험: 상한을 추측해 올리면 메모리와 파일 핸들이 늘 수 있다.
- 검증 방법: 기존 프리셋 테스트. 새 시험을 이번 결과에 기대지 않는다.
- 우선순위: 보류.

## 연결 풀

- 기존 구현: httpx와 httpcore. 전역 슬롯 다음 호스트 슬롯. 공개 모드는 keepalive 0.
- 관찰된 경쟁 제품 동작: WinHTTP와 WinSock2, Qt6Network가 링크되어 있고 WinHTTP DLL은 매핑되어 있다. 동시 연결 수는 미확인이다. TCP 행은 0건이라 풀 크기가 아니다.
- 개선할 구조: WinHTTP로 옮기지 않는다. 호스트 상한은 지금의 프리셋을 유지한다.
- 사용할 공개 오픈소스: httpx 0.28.1, BSD-3-Clause.
- 예상 개발 난이도: 변경 없음.
- 추가 비용: 0.
- 기술적 위험: 풀 구현을 바꾸면 Range 재개와 핀 고정이 다시 깨질 수 있다.
- 검증 방법: 기존 단위 테스트의 호스트 피크 3.
- 우선순위: 보류.

## 비동기 이벤트 루프

- 기존 구현: 다운로드 스레드 하나에 asyncio 루프 하나.
- 관찰된 경쟁 제품 동작: 미확인. Qt 프로세스의 스레드 72와 우리 루프는 같은 구조가 아니다.
- 개선할 구조: 루프를 프로세스 밖으로 늘리지 않는다.
- 사용할 공개 오픈소스: CPython asyncio.
- 예상 개발 난이도: 변경 없음.
- 추가 비용: 0.
- 기술적 위험: 루프를 여럿으로 나누면 취소와 DNS 핀이 어긋난다.
- 검증 방법: 기존 엔진 테스트.
- 우선순위: 보류.

## 메모리 버퍼

- 기존 구현: HTTP 본문을 임시 파일로 흘리고, 확정 전에 길이와 시그니처를 본다.
- 관찰된 경쟁 제품 동작: 미확인. 페이지 파일 416,718,848 bytes는 유휴에 가까운 스냅샷일 수 있고, 버퍼 크기가 아니다.
- 개선할 구조: 큰 메모리 버퍼를 도입하지 않는다.
- 사용할 공개 오픈소스: 없음. 현재 파일 스트리밍.
- 예상 개발 난이도: 변경 없음.
- 추가 비용: 0.
- 기술적 위험: 전체 파일을 RAM에 올리면 대량 작업의 작업 집합이 커진다.
- 검증 방법: 기존 로컬 대량 시험의 작업 집합. 그 숫자와 이번 스냅샷을 비교 수치로 쓰지 않는다.
- 우선순위: 보류.

## 영상 메타데이터

- 기존 구현: yt-dlp 프로브. 재생목록과 DRM은 거절. 크기는 정확한 값만 쓴다.
- 관찰된 경쟁 제품 동작: 메타데이터 화면은 NOT RUN. avformat이 메모리에 있다.
- 개선할 구조: yt-dlp를 유지한다. FFmpeg DLL을 제품에 끼워 넣는 작업은 이번 근거로 시작하지 않는다.
- 사용할 공개 오픈소스: yt-dlp, Unlicense. FFmpeg는 배포 전에 LGPL과 GPL 빌드를 고른다. 아직 우리 패키지에 FFmpeg를 넣지 않았다.
- 예상 개발 난이도: 변경 없음.
- 추가 비용: 0.
- 기술적 위험: GPL FFmpeg를 정적 링크하면 배포 판정이 더 막힌다.
- 검증 방법: 기존 영상 추출 테스트.
- 우선순위: 보류.

## 스레드 분리

- 기존 구현: UI 스레드와 다운로드 스레드, 추출 스레드를 나눈다. WO-04 브랜치는 네트워크 자식을 하나 더 둔다.
- 관찰된 경쟁 제품 동작: 메인 스레드 72, WebEngine 자식 2개. 역할 분리는 미확인.
- 개선할 구조: WebEngine 자식을 따라 만들지 않는다. 동적 페이지는 WO-04의 Playwright를 유지할 후보로 둔다. 그 브랜치는 아직 병합 전이다.
- 사용할 공개 오픈소스: Playwright, Apache-2.0. 이미 WO-04 브랜치에 있다.
- 예상 개발 난이도: 이번 작업에서 구현하지 않음.
- 추가 비용: 0. Chromium 로컬 설치는 WO-04에서 이미 했다.
- 기술적 위험: Qt WebEngine을 중복으로 넣으면 프로세스 수와 라이선스 고지가 늘고, 측정된 이득이 없다.
- 검증 방법: WO-04 보고서의 테스트. 이번 경쟁 제품 스냅샷으로 통과 처리하지 않는다.
- 우선순위: 낮음. 병합 여부는 별도 결정이다.

## 별도 제안

측정이나 호환 필요가 없으므로 구현 대기열에 넣지 않는다.

- ONNX Runtime, DirectML, 음원 분리, 업스케일. DLL과 익스포트 이름만 있고, 이번 프로세스에서는 로드되지 않았고, 모델 파일이 설치 트리에 없다.
- WinHTTP로의 교체.
- Qt WebEngine을 우리 기본 UI에 포함.
- 경쟁 제품의 스레드 72나 페이지 파일 약 397 MB를 목표치로 삼는 튜닝.
- 라이선스 검사나 활성화 경로를 들여다보는 작업.

나중에 같은 로컬 URL로 두 프로그램을 재려면, 4K Video Downloader+가 그 URL을 여는지부터 정상 사용으로 확인해야 한다. 열리지 않으면 지원 불가다. 그 시험은 이번 작업에서 NOT RUN이다.
